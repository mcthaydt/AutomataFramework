# M2 Plan C: the new content files Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task, in
> one session, with no subagents (project rule). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every kind of content file M2 needs (tileset, backdrop, figure, the widened character, behaviour, tuning,
feel, sound, music, cues, conversation, cutscene, messages) can be read, checked with plain `file: path` problems,
written one way, listed in `automata.toml` and read as a published JSON Schema.

**Architecture:** The `content` feature keeps its shape: one file per kind of content, holding that kind's type, Zod
schema, the words for its problems and its checks against other files; `content-types.ts` is the table of them, and
the project file, the loader, the writer and the schema script all work from that table, so a new kind is one file and
one row. Nothing here plays a sound or draws a tile: plans A, S, T, L, I and K build on these files. The one piece of
sim work is small and in the `level` feature: a level that names a tileset takes "solid" from it.

**Tech Stack:** TypeScript 7.0.2 strict, Zod 4.6.6, smol-toml 1.9.0, Vitest 5.0.3 (browser mode on Playwright
1.63.0), Biome 2.5.15, knip 6.39.0, pnpm 10.34.6, Node 24.21.0. No new dependency.

**Spec:** [`docs/superpowers/specs/2026-11-14-m2-design.md`](../specs/2026-11-14-m2-design.md), "Content: the new
files (plan C)", on top of [`2026-11-13-2d-first-layer-design.md`](../specs/2026-11-13-2d-first-layer-design.md).
Principles served: 1 (every new kind of content is a documented JSON file with a JSON Schema and one writer, so an
agent can do all of it with no editor), 2 (one thing per file, numbers with ranges, plain names: the files the M3
editors will change by touch), 3 (2D only), 7 (the old repo is read for what each file needs, and nothing is lifted
ahead of its user).

## Global Constraints

- Zod is the only schema language. Game content is JSON; the project file is TOML. No new dependency.
- Every schema is a `z.strictObject` (an unknown key is a problem), starts with `format: 1` and `id`, and every field
  has a `.describe()` a person can follow. A file's `id` is its file name without `.json`.
- Every problem a person reads is a whole plain sentence that says what to change (the drunk-grandma test). No Zod
  default message reaches a person: Task 2 adds the cases the new schemas need.
- `parseContent`, `parseProject` and `loadGame` never throw. `writeContent` is the only writer.
- A file M1's `writeContent` wrote is, byte for byte, what M2's writes: a new field on `level` or `character` is
  optional and has no default. `tests/fixtures/game/` is not changed by this plan, and no golden in `tests/golden/`
  moves. If one would, stop and report.
- Sorting is by UTF-16 code unit (`sortedKeys` from `src/lib/sorted.ts`, or a bare `.sort()`), never
  `localeCompare`: the bytes must be the same in Node, Chromium, WebKit and Firefox.
- `content` imports only `src/lib/`, `sim`, `physics` and `commands`. A source file has at most 600 lines. Tests live
  in `tests/`, import the code as `#src/...`, and dispose every sim they make.
- Tests run only in GitHub-hosted CI. Locally: `pnpm lint`, `pnpm typecheck`, `pnpm knip`, `pnpm build`,
  `pnpm schemas`, `pnpm api-report --update`. Each task's "run" step is a push and a read of the pull request's CI.
- Before any commit: `git config --global user.name "McThayDT" && git config --global user.email "107786093+mcthaydt@users.noreply.github.com"`,
  and a local hook that refuses any other author. No AI attribution anywhere.
- Units: places and sizes in a level are in **tiles**; times the sim uses are in **ticks** (60 is one second, always
  whole numbers); sound is in **seconds** and **hertz**; pictures are in **pixels**.

## Review Focus

Each has its test in the task named.

1. **A file listed under the wrong kind** (a sound listed as `type = "music"`). Expected: one sentence that says so,
   not a page of "this is missing" and "this is not something a music has" (Task 1).
2. **A thing named like something every object has** (`constructor`, `toString`, `__proto__`): a character, a
   message key or a tile id. Expected: it is an ordinary name, found when it exists and reported as missing when it
   does not (Task 1 for ids, Task 7 for message keys).
3. **A file saved by a Windows editor**: a byte-order mark at the start, `\r\n` line ends. Expected: it reads the
   same as the plain file (Task 2).
4. **A conversation that goes round and round**: node A's `next` is B and B's is A, with no choice and no end.
   Expected: a problem that names the loop, since a player would be stuck in it (Task 7).
5. **A number too big to be a number** (`1e999`, which JSON reads as infinity) or a message in Korean, Chinese or
   with emoji. Expected: the first is "This must be a number."; the second is written to the same bytes in all four
   engines (Tasks 2 and 10).

## The contract: names every task uses

`src/features/content/type-info.ts`:

```ts
export type EditorName = 'world' | 'characters' | 'feel' | 'sound' | 'story'

/** What a check may ask about the rest of the game. */
export interface Listed {
  /** True when automata.toml lists a file of this kind with this id (by file name, so a broken file still counts). */
  has(type: ContentType, id: string): boolean
  /** Every listed id of a kind, sorted. */
  ids(type: ContentType): readonly string[]
  /** The file's value, or undefined when it is not listed or did not read. A check skips what it cannot see. */
  get<T extends ContentType>(type: T, id: string): ContentValue<T> | undefined
}

/** Adds one problem to the file being checked. `path` is written like `things[0].character`. */
export type Report = (path: string, message: string) => void

export interface ContentTypeInfo<Out, In> extends Voice {
  readonly schema: z.ZodType<Out, In>
  readonly title: string          // 'Sound'
  readonly plural: string         // the field of GameContent: 'sounds'
  readonly editor: EditorName     // the M3 editor that opens it
  readonly part: string           // the part of that editor: 'audio'
  /** Puts free keys in one order before the file is written. */
  readonly tidy?: (value: Out) => Out
  /** Checks against other files; runs only when this file read and its id is right. */
  readonly check?: (value: Out, game: Listed, report: Report) => void
}
```

| `type` | TS type | `plural` | `editor` / `part` |
|---|---|---|---|
| `level` | `Level` | `levels` | world / levels |
| `tileset` | `TilesetFile` | `tilesets` | world / tiles |
| `backdrop` | `BackdropFile` | `backdrops` | world / environment |
| `character` | `Character` | `characters` | characters / clips |
| `figure` | `FigureFile` | `figures` | characters / figure |
| `behaviour` | `BehaviourFile` | `behaviours` | characters / schematic |
| `tuning` | `TuningFile` | `tunings` | feel / tuner |
| `feel` | `FeelFile` | `feels` | feel / feel |
| `sound` | `SoundFile` | `sounds` | sound / audio |
| `music` | `MusicFile` | `music` | sound / audio |
| `cues` | `CuesFile` | `cues` | sound / audio |
| `conversation` | `ConversationFile` | `conversations` | story / writer |
| `cutscene` | `CutsceneFile` | `cutscenes` | story / sequence |
| `messages` | `MessagesFile` | `messages` | story / writer |

The table's row order is the one above. New TS types end in `File` because the features that run them (audio, feel,
story) will want the bare names; each schema is `<Type>Schema` (`SoundFileSchema`). `GameContent` is
`{ project } & { [plural]: Readonly<Record<string, value>> }` for all fourteen, every map made with
`Object.create(null)` and frozen.

**Order of problems from `loadGame`:** the project file's own problems; then, for each listed file in the project's
order: its reading problems, or else its id problem, or else its `check` problems.

**Sentences every kind shares** (tests quote them):

- `There is no <noun> called "<id>". This game has: <a, b | nothing>.` (as today)
- `"<id>" is used twice. Each <noun> needs its own id.`
- `This must be one of: a, b, c.`
