# M2 Plan K: the `automata` command, MCP and skills Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task, in
> one session, with no subagents (project rule). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One command, `automata`, with which an agent or a person makes a new game (`create`), is told in plain words
whether it is sound (`check`), runs it (`play`), plays a recording to its hash (`replay`) and paints its art (`art`);
the same commands as an MCP server (`mcp`); and skills in the package that say where things live and how to add each
kind of content.

**Architecture:** A new Node-only feature, `cli`, at the top of the layers, reached only through a fourth build entry,
`src/cli.ts`, which the package names as its `bin`. Each command is an Effect program over four small ports (the
files, the game's own tools, the game's code, the output), so every command runs in a Node test on files in memory.
A game is always read and run with the framework that game installed, loaded from the game's own folder, so the
command and the game's rules share one copy of the sim. The template `automata create` writes is a real game kept in
this repo at `template/`, checked by this repo's CI like any game and shipped in the package. The MCP server is our
own small one over stdio, and it calls the same functions the commands call.

**Tech Stack:** TypeScript 7.0.2 strict, Effect 3.22.2 (Node tooling, as the stack table says), Zod 4.6.6, Vite 8.3.3,
Vitest 5.0.3, Playwright 1.63.0 (journeys), Biome 2.5.15, knip 6.39.0, pnpm 10.34.6, Node 24.21.0. **One new
dependency is asked of the Owner and held until answered** (Q1 below): `@modelcontextprotocol/sdk` 1.32.2, for
development only.

**Spec:** [`docs/superpowers/specs/2026-11-14-m2-design.md`](../specs/2026-11-14-m2-design.md), "The agent tools (plan
K)", "M1's deferred minors" (M4, M5 and M9), the Goals' "a first-time developer or agent goes from the README to a
new, running game that passes `automata check`", the anti-goal "a feature the demo game has that a new game from
`automata create` does not get for free", the Testing line "a test follows the README in a clean folder", and the
second line of "Done means"; on top of
[`2026-11-13-2d-first-layer-design.md`](../specs/2026-11-13-2d-first-layer-design.md) (layer 15, `cli`, and "Agent
skills ship with the package"). Principles served: 1 (every command prints plain words and `--json`, every MCP tool is
a command an agent can also type, and the skills are files in the package), 2 (the template's page is touch first and
its journey runs at phone and tablet sizes), 3 (2D only; the command is the last 2D layer), 4 (one package: the
command is in the framework, not a second one), 6 (Effect for Node tooling, as carried over; one dependency asked

## My calls (the builder's, inside the spec)

None needs an answer before execution; the plan audit may challenge any of them.

1. **The command is in the framework's own package,** as a `bin`, not a second package: the spec's layer list ends in
   `cli`, and "no monorepo" means one package per repo. A game runs it from its own install, through its `npm run` scripts or `npx --no automata` (audit I1).
2. **A game is read and run with the framework that game installed.** `automata check` in a game loads
   `node_modules/@automataframework/framework` from that game's folder and the game's `src/headless.ts` beside it,
   so the rules and the sim are one copy and the answer is the one that game's page would give. `create` is the one
   command that uses the command's own copy, because there is no game yet.
3. **A game's rules are found by one name.** `src/headless.ts` exports `gamePlugins`, the list the page, the tests
   and the command all build their sim from. The demo game already does this; the check says so in a sentence when
   it is missing. A game's files are loaded as they are (Node 24.21.0 runs TypeScript that only has types to take
   out), so the template's `tsconfig.json` sets `erasableSyntaxOnly` and every import of a file ends in `.ts`.
4. **Changed content is a note, not a failure.** A replay records the content's hash; an editor's whole job is to
   change content. So in `check`, `content-changed` passes and says how to record again; `code-changed` and
   `diverged` fail. This is the rule the demo's own replay test already keeps.
5. **`automata replay --accept` is how a recording is taken again:** the same commands, played on the game as it is
   now, with the new hashes written. An agent that meant to change the play runs it and says so in its commit. (In
   this project's own repos a golden still moves only with the Owner seeing before and after; that is our process,
   not the tool's.)
6. **`automata create` leaves the game's name as "My Game".** The project's name is part of the content hash, so
   writing another name would make the template's recording stale on the first check. The folder's name goes into
   `package.json` and the saves' id; the README's second step is "give it a name", which also teaches `--accept`.
7. **The template names no package manager and the README uses npm,** because npm comes with Node and the first
   section must be a handful of commands. The command starts the game's tools (`biome`, `tsc`, `vitest`, `vite`)
   straight from the game's `node_modules/.bin`, so pnpm works as well and nothing depends on which was used.
8. **"A running game's state" for an agent is a headless session,** a sim in the MCP server's own process that the
   agent steps and reads, not a browser it cannot see. `automata play` (a browser, for a person) is not an MCP tool.
   Everything a session does can also be done by typing: write a replay file, then `automata replay <file> --state`.
9. **Skills are read from the installed package,** at `node_modules/@automataframework/framework/skills/`, so they
   are never older than the framework they describe. The template's `AGENTS.md` names each one and says to read it,
   its `CLAUDE.md` is one line that includes `AGENTS.md`, and `automata mcp` serves them as resources and through a
   tool. Agent tools load skills from their own folders, not from `node_modules`, so nothing here claims they load by
   themselves (audit M14).
10. **No parser is added for the rules step.** The old command read code with `oxc-parser`; this one reads imports
    and the forbidden names with the patterns `tests/architecture/rules.ts` already uses, moved to `src/lib` and
    shared. It can be fooled by a string that looks like code; `types` and the replays catch what matters.
11. **`check` runs in Node only.** Playing a game's replays in three browsers is this repo's and the demo's CI; a new
    game's own CI workflow (in the template) runs `automata check`. A `--engines` flag is one step to add when a
    game asks.

## Global Constraints

- **The command changes nothing in the sim.** Nothing under `src/features/` but `cli` imports `cli`. `cli` imports
  only headless features, through their entries, and never `render`, `input`, `web`, `game` or `server`.
- **No recorded hash moves.** No file under `tests/golden/` is changed by any task. Task 2 changes how a replay is
  written, not what a sim computes; if a test that reads a golden fails, stop and report.
- **One new golden in Part 1:** `template/replays/level-1.json`, recorded in CI (Task 7), in a commit that names it.
  A Part 2 step that changes the template's play records it again in a commit that names it and shows the Owner the
  hashes before and after.
- **Every sentence a person reads says which file and what to do,** and passes the drunk-grandma test. No stack
  trace reaches a person: an error nobody planned for prints `Something went wrong inside automata. Please report
  this:` and then the error, and exits 2.
- **Exit status, for every command:** 0 everything is fine; 1 the game has something to fix; 2 the command could not
  do its work (a tool is missing, a folder is not a game, the words after `automata` make no sense).
- **`--json` on every command but `play` and `mcp`** prints one JSON value on stdout and nothing else there.
- Effect is imported only under `src/features/cli/` and in `src/features/server/process.ts`. Zod is the only schema
  language. No `any`.
- A tool is started with a list of arguments, never a shell string, and paths are joined with `node:path`, so a
  folder with a space in its name and a Windows path both work.
- A source file has at most 600 lines. Features import only features below them, through the entry file.
- Comments say why. Every exported name has a doc comment.
- **Nothing is run locally**: no test, and no `pnpm` command either (the coordinator, 2026-11-14). Every check is a
  pull request's CI run, read with `gh run list --branch <branch>` and `gh run view <id> --log-failed`.
- No Claude attribution anywhere; commits are by `McThayDT <107786093+mcthaydt@users.noreply.github.com>`, set before
  every commit and held by a local hook that refuses any other author.
- No strategy, market, competitor or pricing words in the README, the skills, the template or the help.
- **Never a bare `npx automata`** in anything a game ships or a person reads (audit I1): npm has an unrelated package
  called `automata`, and `npx` fetches it, without asking when its input is not a terminal, wherever a game's install
  is missing. A person types an `npm run` script (`dev`, `check`, `fix`, `test`, `accept`); an agent is told
  `npx --no automata <command>`, which never fetches; `.mcp.json` starts `node` on the bin's file. The words test
  (Task 7) and the skills test (Task 10) fail on `npx automata`.
- **The goldens of this plan** (audit I3) are `template/replays/level-1.json` and `tests/golden/schema-hash.json`.
  Either changes only with the Owner seeing the hashes before and after, in a commit that names it.

### Task 11: `automata mcp`: the server and the tools over the commands

**Do not start before Q1 is answered** ("For the Owner"). Written for answers (a) and (b), which share it.

**Files:**
- Create: `src/features/cli/mcp.ts`, `mcp-tools.ts`, `tests/features/cli/mcp.test.ts`, `mcp-tools.test.ts`
- Modify: `src/features/cli/cli.ts`, `help.ts`

**Interfaces:**
- Produces: `serveMcp(input: AsyncIterable<string>, write: (line: string) => void, layer: Layer.Layer<Ports>): Promise<void>`
  (one JSON message per line each way; resolves when the input ends);
  `TOOLS: readonly McpTool[]` with `McpTool = { name: string; description: string; inputSchema: z.ZodType; run: (input: unknown) => Effect<unknown, CliError, Ports> }`;
  `PROTOCOL_VERSIONS: readonly string[]`, newest first.

The protocol is JSON-RPC 2.0 over stdio, one message per line, as the MCP specification's stdio transport says.
Read the specification at `modelcontextprotocol.io/specification` on the day of execution and trust it over this
paragraph. The server answers `initialize` (with the client's protocol version when it is one of
`PROTOCOL_VERSIONS`, else our newest; capabilities `tools` and `resources`; `serverInfo` `automata` and the
framework's version), `ping`, `tools/list`, `tools/call`, `resources/list` and `resources/read`; takes
`notifications/initialized` and any other notification in silence; answers an unknown method with `-32601`, a line
that is not JSON with `-32700`, and arguments a tool's schema refuses with `-32602` and a sentence. A tool's answer
is one text block holding JSON; a `CliError`, or a check that found problems, is a result with `isError: true`,
never a protocol error, so an agent reads the sentences.

While the server runs, `console.log`, `console.info` and `console.debug` are pointed at stderr, so a game's rules
that print cannot break the protocol.

**The server never imports a game's code itself** (audit C1). Node keeps every module it has imported for the life of
the process, so a server that loaded `src/headless.ts` once would answer from those rules after an agent changed them.
`create`, `check` and `replay` therefore run through `Runner.command`: the package's own `dist/cli.js`, started with
`process.execPath`, the command's words and `--json`, in the folder, whose JSON and exit code become the tool's
answer. That makes the "same as typing" column below literally true, and keeps Koota's sixteen worlds a process out of
the server's way. The memory layer's `Runner` calls `main` with the same words, so every test here still runs in
memory.

The tools in this task (the play sessions are Task 12):

| Tool | Input | Answers | The same as typing |
|---|---|---|---|
| `create` | `folder` | the folder and the files written | `automata create <folder> --json` |
| `check` | `folder`, `only?`, `fix?` | the `CheckReport` | `automata check <folder> --json` |
| `replay` | `folder`, `file?`, `accept?`, `state?` | the `ReplayResult`s | `automata replay <folder> --json` |
| `content_types` | none | each kind: its folder, what it holds, its schema's resource | reading the README's table |
| `schema` | `type` (a kind, or `replay`) | that JSON Schema | reading `schemas/<type>.schema.json` |
| `skill` | `name?` | the skills' names and descriptions, or one skill's text | reading `skills/<name>/SKILL.md` |

Resources: `automata://schemas/<type>` for every kind and `replay` (`application/schema+json`), and
`automata://skills/<name>` for every skill (`text/markdown`). Each tool's `inputSchema` in `tools/list` is the JSON
Schema of its Zod schema; every description is one plain sentence that says when to use the tool.

`mcp --help` prints:

```
automata mcp

Lets an agent use automata's commands as tools, over the Model Context Protocol. An agent's own program starts
this; it waits for messages and prints nothing a person reads. A game made by automata create is already set up
```

- Produces: `SessionWorker` (the contract's `Runner.worker`: `call(message)`, `end()`), the worker's own file
  `src/features/cli/session-worker.ts`, and `createSessions(max?: number): Sessions` (default 4) with
  `start(options: { folder: string; level?: string; players?: readonly number[]; seed?: number }): Effect<{ session: string; state: GameState }, CliError, Ports>`,
  `step(session: string, ticks: number, hold: Readonly<Record<string, readonly string[]>>): { state: GameState; events: readonly string[] } | CliError`,
  `state(session)`, `save(session, file): Effect<{ file: string; ticks: number; finalHash: string }, CliError, Files>`,
  `stop(session)`, `stopAll()`.

A session is one sim with a recorder, in a `node:worker_threads` Worker that `play_start` starts and `play_stop` ends
(audit C1): a Worker has its own modules, so a session started after the agent changed the rules plays the new ones,
and `play_start`'s answer says `This session plays the game's rules as they were when it started.` The memory layer's
worker runs the same session code in the test's own process. `step` holds, for each player named (`"1"`,
`"2"`), those actions for that many ticks (1 to 3,600, a minute of play), sending one `controls` command per player
per tick the way the page's input does, and answers the state and the ids of the events raised, in order, each id
once per tick, the first 200. A player not named holds nothing. An action the game does not have, or a player not
in the game, is refused with its sentence from "The words" before any tick is played (audit M11). `save` writes the recording so far to
`replays/<name>.json` (`file` is that name: letters, digits and dashes), with `meta` `level` and `players`.
Session ids are `s1`, `s2` and so on. Every session is disposed on `stop`, when the server's input ends, and when
its game's rules throw (the answer then says `The game stopped at tick <n>: <message>.` and the session is gone).

| `play_state` | `session` | `state` |
| `play_save` | `session`, `file` | the file written, its ticks and final hash |
| `play_stop` | `session` | `stopped: true` |
