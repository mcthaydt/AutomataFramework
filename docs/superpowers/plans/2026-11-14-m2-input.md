# M2 Plan I: Input (gamepad, changing keys, up to four players) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task, in
> one session, with no subagents (project rule). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A game made with the framework is played with a keyboard, the touch buttons or a gamepad, all mapped to the
same actions; a player can change which key or button does what and keep the change; and up to four people play on
one screen, each with their own device, joining and leaving while the game runs.

**Architecture:** The sim still sees only commands. The `input` feature grows from "one player's keyboard and touch"
to a small set of pure parts (reading a pad, who holds which device, what a player is holding, changing a binding)
wired together by `input.ts`, which sends one `controls` command per player whose hands changed. Joining and leaving
are two new commands, `join` and `leave`, handled by a plugin in the `level` feature that a game gets only when its
`automata.toml` says `players = 2` or more, so a recorded play shows who joined when and no existing golden moves.

**Tech Stack:** as on `main`: TypeScript 7.0.2 strict, Koota 0.6.6, Rapier 2D deterministic 0.21.0, Zod 4.6.6,
Vitest 5.0.3 in browser mode on Playwright 1.63.0, Biome 2.5.15, knip 6.39.0. The browser's Gamepad API. **No new
dependency.**

**Spec:** [`docs/superpowers/specs/2026-11-14-m2-design.md`](../specs/2026-11-14-m2-design.md), "Input (plan I)" and
"Multiplayer in the demo", over the [first layer's spec](../specs/2026-11-13-2d-first-layer-design.md). Principles
served: 1 (controls, saved bindings and joins are plain data an agent can read and write; a join is a recorded
command), 3 (2D only), 6 (no new dependency), 7 (the pad reading and the test pad are ported from the old repo, for
this layer only).

Plan I is the framework's input layer. It has no dependency on another M2 plan and must not wait for one.

|---|---|---|

| "A level is done when every player is through the door"; the demo's co-op golden; the demo's journeys | Plan D (Examples) | the `join` and `leave` commands in the replay; see "Plan D's step for input" |
| Online play | Plan N | the same `join`, `leave` and `controls` commands, numbered per player |

**End-to-end here** means the whole game, started with `startGame` in real Chromium, WebKit and Firefox, driven by
real key and pointer events and by a pretend gamepad installed as `navigator.getGamepads` (no browser driver can plug
in a real one). Those are Task 9's tests. The spec's two demo journeys for input ("a player changes a key and uses
it", "a second player joins with a gamepad and both reach the door") run against the built demo in Examples and are
plan D's; Task 9 is their twin at the framework's level.

## My calls (the builder's, inside the spec)

Each follows from something the Owner already decided. None needs an answer before execution; the plan audit may
challenge any of them.

1. **Co-op is switched on per game, by `players = 2` to `4` in `automata.toml`.** The Owner's rule is "every game is
   built as if it were multiplayer; turning it on is a per-game choice". A game without the line is as it is today,
   to the byte: the sim's hash covers its commands and systems, so adding `join` to every game would move every
   golden in this repo and in Examples. The template `automata create` makes (plan K) can carry the line.
2. **With one player, every device drives that player.** Keyboard, touch and any gamepad: nothing to set up. A second
   person joins through "Add a player" (plan U's screen calls `invite`), never by bumping a pad mid-game.
3. **A joining player brings one device:** a gamepad, or the second half of the keyboard. Touch never joins (the
   spec: touch is one player only). The lowest-numbered player has everything nobody else brought.
4. **A new hero starts at its own start point** in the level.
5. **Changing a key swaps, never refuses.** If the new key belonged to another action that would be left with
   nothing, that action takes the old key.
6. **Kept for menus, never bindable:** the keys `Escape` and `Tab`, and the gamepad's `start` and `home`.
7. **Bindings are per device kind, not per player:** one set of keys, one set for each half of a shared keyboard, one
   set of gamepad buttons. The spec has one settings slot.

/** The game's controls with the player's saved changes. Never throws: what no longer fits is dropped and named. */
export function applySettings(defaults: Controls, saved: unknown): { readonly controls: Controls; readonly dropped: readonly string[] }

export type Rebound =
  | { readonly ok: true; readonly controls: Controls; /** The action that gave the input up and took the old one. */ readonly swapped?: string }

  Rules. `rebind`: every other action loses `input` in the same slot; one left with nothing takes what the action
  just gave up (`swapped` names it; if two would be left empty, the first in the controls' order takes it and the
  result must still pass `checkControls`). `applySettings`: `saved` that does not parse gives the defaults and
  `dropped: ['*']`; otherwise overrides are applied one action at a time in sorted order, and one is dropped (its
  action's defaults stand) when the action does not exist, or when the controls with it would fail `checkControls`.

### Task 4: Who holds which device, and what they are holding

**Files:**
- Create: `src/features/input/seats.ts`, `src/features/input/held.ts`
- Test: `tests/features/input/seats.test.ts`, `tests/features/input/held.test.ts`

**Interfaces:**
- Consumes: `Controls`, `PadInput`, `Device`, `Claim`, `Seat`.
- Produces:

```ts
/** `players`: who is in the game. `claims`: what each joining player brought. `pads`: indexes of usable pads now. */
export function seatsFor(players: readonly number[], claims: ReadonlyMap<number, Claim>, pads: readonly number[]): Seat[]
export interface Down {
  readonly keys: ReadonlySet<string>                               // key codes
  readonly touch: ReadonlySet<string>                              // action names
  readonly pads: ReadonlyMap<number, ReadonlySet<PadInput>>       // by pad index
}
/** The actions this seat's player is holding, sorted. */
export function heldBy(seat: Seat, controls: Controls, down: Down): string[]
```

  `seatsFor`, one seat per player, ascending:
  1. The first player is the lowest number. Every other player with a claim holds exactly that: `pad-N`, or
     `keyboard-2` for a `keyboard` claim.
  2. The first player holds everything nobody else holds: `touch`, every pad in `pads` no other player claims, and the
     keyboard, whole (`keyboard`) unless another player claims it, then `keyboard-1`. The first player's own claim is
     ignored.
