# M2 Plan P: joints and touch Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task, in
> one session, with no subagents (project rule). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A level file can pin a thing or hang it from a rope, a character file can say it is touched and not bumped
into, and the sim tells the game about each touch by name, all of it on one hash in Node, Chromium, WebKit and Firefox.

**Architecture:** Joints live where bodies and colliders live: a `Joint` component in the `physics` feature, made into
a Rapier joint by the same sync-in that makes bodies, in a fixed order, and kept in the physics bytes of a snapshot.
Touch is the `level` feature's: a character with `touch` gets a sensor collider, and a small plugin turns the physics
feature's collision events into events named after the character's kind. Both are switched on by the game's content,
so a game that uses neither has exactly the sim it has today.

**Tech Stack:** TypeScript 7.0.2 strict, `@dimforge/rapier2d-deterministic-compat` 0.21.0, Koota 0.6.6, Zod 4.6.6,
PixiJS 8.22.0, Vitest 5.0.3 (browser mode on Playwright 1.63.0), Biome 2.5.15, knip 6.39.0, pnpm 10.34.6, Node
24.21.0. No new dependency.

**Spec:** [`docs/superpowers/specs/2026-11-14-m2-design.md`](../specs/2026-11-14-m2-design.md), "Physics: joints and
touch (plan P)" and the showcase table's Physics row, on top of
[`2026-11-13-2d-first-layer-design.md`](../specs/2026-11-13-2d-first-layer-design.md). Principles served: 1 (a seesaw,
a swing, a spark and a door are lines in a JSON file an agent can write, checked with plain sentences), 2 (a joint is
placed by a point on the level, which is what a finger drags in the M3 World editor), 3 (2D only), 6 (Rapier's
deterministic build, with parity in four engines), 7 (nothing is lifted: the old repo had no joints).

## What this plan covers, and what it does not

Covered: reading this tick's events inside the sim; the `Joint` component and its two kinds; joints in a snapshot;
`joints` in a level file and `touch` in a character file; spawning both; the touch events; ropes and pins drawn as
plain lines; a fixture game with a seesaw, a swing, a spark and a door; goldens and parity; a journey in three real
browsers by key and by touch button; the packed package; the README.

Not covered, and whose it is:

| Not here | Whose |
|---|---|
| The seesaw, the swinging platform, the sparks and the door in the demo game | Plan D (its step for plan P, below) |
| "The level is done when every player is through the door", counting sparks | The game's own code (plan D), from the events here |
| A sound or a freeze when a spark is taken | Plans S and the feel runtime: their files name `spark.taken` |
| Art for a rope, a pin, a spark | Plan A: this plan draws a dark line and a dot, so nothing hangs in the air unexplained |

**Left out, with reasons.** Sliding, welded and spring joints, and motors: the showcase uses none, and a kind is one
row in `JointKind`, one variant in `level.ts` and one case in `rapier.ts` when a game needs it. A touched character
that moves (a `dynamic` body with `touch`): it would fall through the floor, so the file is refused with a sentence.
Joints on a hero: heroes come and go (plan I), so a level's joints name things only. Platforms you can jump up
through, ray casts, a joint that breaks: no user in M2.

## My calls (the builder's, inside the spec)

None needs the Owner. The plan audit may challenge any of them.

1. **Switched on by content, never for everyone.** The sim's schema hash covers every component, event and system
   (`create-sim.ts`), so adding `Joint` to every sim would move `push-crate.json`, `physics-scene.json`, `bounce.json`
   and both of Examples' goldens. `physics({ joints: true })` adds the component; `createGameSim` passes it when any
   level of the game lists a joint, and adds the touch plugin when any character has `touch`. Plan I made the same
   call for `join`.
2. **Two kinds: `pin` and `rope`.** A seesaw is a plank pinned to the level; a swing is a platform on two ropes.
3. **A joint is placed by points on the level, in tiles,** not by offsets from a body. That is what a person sees and
   drags; the offsets Rapier needs are worked out when the level is spawned.
4. **Pinned things pass through each other; roped things do not.** A hinge sits inside both of its parts; two crates
   tied together should still bump.
5. **Events are named after the kind** (`spark.taken`), not one event with the kind inside it, because a cue or a
   feel file answers an event by name alone (plan C's `on`).
6. **`take` is built in.** Taking something away when a hero touches it is the commonest rule a platformer has. What
   the taking means (a score, a key) is still the game's.

**The order of work in sync-in** (a contract, like the one in `physics-world.ts` today; each step lowest sid first):

1. Decide, without touching Rapier, which body rows step 3 will remove (an entity that no longer qualifies as it
   did).
2. Remove every joint whose entity is gone or has no `Joint`, whose fields differ from the ones it was built from,
   or either of whose bodies step 3 will remove.
3. Remove body and collider rows (as today).
4. Create body and collider rows (as today).
5. Update bodies and colliders (as today).
6. For each entity with `Joint` and no joint row: validate it; then, if `a` and `b` are both alive with body rows,
   create the joint. If either is missing the joint waits, with no error, and is tried again next tick.

Rapier removes a body's joints by itself when the body goes. Step 2 comes first so that never happens: the table and
the world always agree. Creating and removing a joint wakes both bodies.

**The physics bytes.** A world made with `joints: false` writes version 2, byte for byte as today. A world made with
`joints: true` writes version 3: version 2's layout, with a joint table between the contacts and Rapier's bytes:
`u32 count`, then per joint in ascending sid: `u32 sid`, `f64 handle`, `f64 bodyA`, `f64 bodyB`, `u8 kind`, `u32 a`,
`u32 b`, `f32 ax, ay, bx, by`, `u8 limited`, `f32 min`, `f32 max` (54 bytes). A world refuses any version but its
own. The joint's fields are in the bytes so that, after a restore, "do the fields differ" is answered from the table
and never by asking Rapier (the lesson of `rotationLocked` in `rapier.ts`).

**Sentences** (tests quote them):

- Level file: `There is nothing called "plnk" in this level. It has: crate-1, plank.`;
  `A hero cannot be joined to anything. Join a thing from this level's "things".`;
  `A thing cannot be joined to itself. Leave "holder" out to join it to the level.`;
  `"min" must be less than "max".`; `A rope needs some length. Move its two ends apart, or give it "slack".`;
  `The character "wall" is "fixed", so it never moves and cannot be joined to the level. Make it "dynamic", or remove this joint.`
- Character file: `A character that is touched needs a "kind", so the game can say what was touched.`;
  `A character that is touched lets everything through, so it would fall out of the level. Make its body "fixed".`
- Physics errors: `entity 7: physics.joint.kind is 9; expected a JointKind (0..1)`;
  `entity 7: physics.joint.b is 7; a joint needs two different entities`;
  `entity 7: physics.joint.max is 0; a rope's length must be positive`;
  `entity 7: physics.joint.min is 1; it must not be more than max (0.5)`;
  `entity 7: physics.joint.ax is NaN; it must be a number`.
