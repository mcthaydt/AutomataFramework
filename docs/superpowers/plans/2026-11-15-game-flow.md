# Plan U: The Default Game Flow Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task, in
> one session at a time, with no subagents (project rule). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every game made with the framework opens the same way without a line of its own code: Warnings (if needed),
the Language picker, the Splash, the Main menu, Gameplay (with pause), and back to the Main menu, played by thumb
first, then gamepad, then keyboard.

**Architecture:** Three new page features. `ui` is the small Svelte 5 kit (button, slider, toggle, list, key row,
dialog, frame) with focus that follows arrows and a gamepad. `screens` is one screen per file pair (rules in a `.ts`
with no page, the look in a `.svelte`), each a function a game can replace. `flow`, the top page feature, is one pure
state machine (`steps.ts`) and `startFlow`, which loads the game, walks the steps, and starts and stops `startGame`
level by level. What the flow shows comes from files: `automata.toml` gains `levels`, `done`, `warnings` and `splash`,
and every word is a key in the framework's library that a game's own messages file can answer first. None of it is
given to the sim, so no hash moves.

**Tech Stack:** TypeScript 7.0.2 strict, Svelte 5.57.1 (the spec's stack), Zod 4.6.6, Vitest 5.0.3 (browser mode on
Playwright 1.63.0), Biome 2.5.15, knip 6.39.0, pnpm 10.34.6, Node 24.21.0. **Two new development packages, approved
by the Owner (Q1, 2026-11-15):** `@sveltejs/vite-plugin-svelte` 7.3.1 and `svelte-check` 4.7.6, the versions
AutomataFrameworkEditors already uses (on TypeScript 6.0.3 there, not 7: see Task 5).

**Spec:** [`docs/superpowers/specs/2026-11-14-m2-design.md`](../specs/2026-11-14-m2-design.md) ("UI, screens and
layouts (plan U)", "Watch mode", "M1's deferred minors", "Multiplayer in the demo"), with the order of the flow from
[`2026-11-14-no-default-language-design.md`](../specs/2026-11-14-no-default-language-design.md) (the Owner's answer Q2,
and "The picker") and the two touch settings from
[`2026-11-14-content-hero-controls-design.md`](../specs/2026-11-14-content-hero-controls-design.md) ("How it is
played"). Read all three first; this plan argues from them and does not repeat their reasons.

**Principles served:** 1, agent-first (the levels' order, what ends a level, the warnings, the splash and every word
on every screen are fields and keys in documented files; nothing about the flow lives only in code or on a screen);
2, iPad-first (every screen is designed at phone size first and proven by touch at five sizes); 6, the stack carries
over (the Svelte kit the stack names); 7, port in layer order (the old repo's kit and screens, reviewed as they land).
It also serves the two standing rules: the drunk-grandma test and onboarding first. It breaks none: 2D only, one
package, nothing built ahead of its user.

## Global Constraints

- **No golden moves.** `tests/golden/*`, `template/replays/level-1.json` and the Examples goldens keep their hashes.
  The four new fields of `automata.toml` are taken out of what the sim is given (Task 1). If a recorded hash differs
  in CI, stop that task and report it. Never re-record.
- **Mobile first** (the Owner, 2026-11-14): most players are on phones. Every screen is designed and tested at
  390 by 844 first. Input priority is touch, then gamepad, then keyboard and mouse. Nothing on a screen is a desktop
  control pasted onto a phone: no hover-only state, no small close cross, no control at the top of a tall phone that
  a thumb cannot reach when the same control fits at the bottom.
- **Touch targets:** every control is at least 44 CSS pixels in both directions and every primary action at least
  48, at every size in `tests/fixtures/game/screens.ts`. Never shrink one to make a screen fit; scroll only inside
  the one region a screen declares.
- **Every action works three ways:** by touch, by gamepad (the D-pad or left stick walks, the bottom button
  presses, the right button goes back, start pauses) and by keyboard (arrows, Enter or Space, Escape).

- **The order of the flow is the Owner's** and is not reopened: Warnings (if needed), Language picker, Splash, Main

- **A game changes the flow through files, not code:** `automata.toml` for what shows, its messages files for the

## The builder's calls

The spec leaves these to the builder, or is silent. They are settled here so the executor makes none of them.

1. **Three features, in this order in `LAYERS`:** `…, 'locale', 'web', 'ui', 'screens', 'game', 'flow', 'cli'`.
   `screens` sits below `game` and takes what it needs as small structural types (`Pick<Input, …>`), never the
   `Game`. `flow` is the only feature that imports `game`. All three are page features.
2. **The kit is compiled into the framework's files** and its styles travel inside the scripts
   (`compilerOptions.css: 'injected'`), so a game made by `automata create` needs no Svelte plugin and no stylesheet
   to get the screens. `svelte` is a `dependency`, left for the game's bundler like PixiJS, so a game that writes its
   own Svelte screen shares one runtime. A page whose header forbids inline styles would show the screens unstyled;
   the Site's header allows them, and M4's host adapters own any stricter host.
3. **A part's props are a plain interface in `ui/props.ts`**, and the part is exported as
   `Component<ThatProps>`. The public surface, the API report and `isolatedDeclarations` then see only TypeScript.
4. **A level ends when the sim raises the event the game names** in `automata.toml` (`done = "door.touched"`), or
   when the game's code calls `flow.finishLevel()`. The framework adds no event to any sim, which is why no hash
   moves. An event whose payload has a number `player` counts only when it is 1 or more (audit I7): a touch event
   names its toucher, and `player` is 0 when that was not a hero, so a crate pushed into the door does not end the
   level. Any other event counts the first time it is raised. A game with no `done` has levels that never end by themselves; the pause screen leaves them.
5. **Levels are played in the order of `levels`** in `automata.toml`. Left out, the game is its `start` level alone.
   Each level is its own `startGame` and its own recording.
6. **Progress is a save of the game's own shape that has a `level`.** With no `save` option the flow keeps
   `{ level }` in three places a player sees as "Game 1" to "Game 3". "Continue" opens the newest. "New game" takes
   the first empty one, and asks before writing over one when none is empty. The level reached is written when a
   level is done and there is a next one.
7. **The main menu's buttons**, top to bottom, the first one focused: Continue (only with a saved game), New game
   (called Play when nothing is saved yet), Saved games (only with one), Add a player (only in a game with
   `players`, while there is room), Settings, Quit (only where `host.canQuit`).
8. **Pause** is a 48 pixel button in the top corner on the side away from the jumping thumb, inside the safe area;
   Escape; the gamepad's start; and the page leaving the screen. A game paused because the page left stays paused
   until the player presses "Keep playing". Music plays on under the pause (plan S's default).
9. **The splash lasts 2000 ms on the game's own frames** (the injected `Frames`, never `setTimeout`), so a test
   moves time by hand, and any tap, key or gamepad button ends it at once.
10. **A second player joins from the main menu before the game exists.** `padMenu`'s listener is told which pad
    pressed (Task 2), the flow keeps who plays (`party.ts`), and each level starts with them. During play, "Add a
    player" on the pause screen uses `game.input.invite` and `game.addPlayer` as plan I built them.
11. **Settings opened from the main menu, where no game runs, makes an `Input` of its own** on an element that is
    never put on the page, so changing a key is the same code in both places. It is destroyed when Settings closes.
12. **The flow makes one `GameAudio` for the whole visit** (when the game has cues), over `webSpeaker({ host })`,
    and passes `soundNotice: false`: Settings says what the sound is doing. It raises page events a game's cues file
    may answer, listed in `FLOW_EVENTS`: `screen.menu`, `screen.pause`, `screen.done`, `ui.move`, `ui.press`,
    `ui.back`.
13. **Watch mode:** `startFlow({ watch })` plays the recording first with the Owner's words ("The game is playing by
    itself. Tap it to play."). A tap, a key, a gamepad button or `flow.takeOver()` goes on to the warnings and the
    picker when they are owed, then straight into the main menu's first action (the spec: "Play goes to the title
    screen's first action"). The splash and the menu are skipped that once. `postMessage` stays the demo's own code.
14. **Online games are not in the flow.** `startOnlineGame` keeps its own page. Nothing here uses it, and the demo
    does not go online. The pause-must-not-stop-the-room note (plan N, N3) is handed on.
15. **`mount.dataset.state` is the flow's step** (`loading`, `watching`, `warnings`, `picking`, `splash`, `menu`,
    `playing`, `paused`, `done`, `problem`) and `mount.dataset.over` the screen on top (`settings`, `saves`,
    `players`, or empty). A journey and an agent read the same two attributes.
16. **Icons are seven SVG files drawn here** (`src/features/ui/library/`: pause, play, back, gear, plus, check, and
    reload for the problem screen before there is a language; audit M3). No icon package: Phosphor is approved for
    the other three repos, not this one.
17. **A broken game** (its code threw in a step) stays stopped, and the flow shows one screen: "The game stopped."
    and "Load the page again". The error is thrown again after the screen is told, so a developer's console has it.

export interface FlowState {

  /** The screen on top of `menu` or `paused`. */
  readonly over?: Over
  /** The level being played, in `playing`, `paused` and `done`. */
  readonly level?: string
  /** The warnings have been shown this visit. */
