# M2: the 2D framework in full, and the demo game as its showcase

Written 2026-11-14. Stage 1 (Spec) of the project workflow, for milestone 2 of the
[2D first layer](2026-11-13-2d-first-layer-design.md). That spec still holds; this one says what M2 builds, in what
order, and how it is proven. Where the two differ, this one is newer and says so.

## Principles served

| Principle | How M2 serves it |
|---|---|
| 1. Agent-first | Every new kind of content (sounds, music, conversations, cutscenes, behaviour rules, feel, tilesets, backdrops, figures) is a documented JSON file with an exported JSON Schema. The `automata` command (`create`, `check`, `play`, `replay`, `art`, `mcp`) and the agent skills let an agent do everything a person can, with no editor. |
| 2. iPad-first editors | M2 builds no editor, but every content file it adds is the file an M3 editor will change, so it is shaped for touch editing (one thing per file, numbers with ranges, plain names). The game's own screens are touch first and tested at phone and tablet sizes. |
| 3. Layers in order | M2 finishes the 2D runtime before the editors (M3) and long before 3D. No 3D code. |
| 4. Separate repos | Framework work lands in AutomataFramework; the demo game grows in AutomataFrameworkExamples, using only the published package. |
| 5. Builders carry over | The painting half of the figure and environment builders (a figure or scene file turned into 2D art) arrives in the framework as `automata art`, so the demo has real art in M2 and the M3 builders are screens over it. |
| 6. Stack carries over | Svelte 5, Paraglide, Colyseus and Effect join in M2, as the M1 spec's stack table names them. Nothing else is added without the Owner's yes. |
| 7. Port in layer order | Each M2 plan ports the old repo's piece for its own layer only, reviewed as it lands, with the source commit noted. |

## Why

M1 proved the four repos meet: a crate moved on an iPad lands in the game and on the site. It did that with a game
that has one level, a hero and a crate. Claim 1 ("the part after the demo is already done") is not true yet: there are
no screens, saves, sound, gamepad, languages or multiplayer. Claim 2 ("built for agents") has the formats but not
the command, the MCP server or the skills. M2 makes both claims true, and the demo game proves them by showing every
one to anyone who plays it (the Owner, 2026-11-14: the demo is a showcase of every core feature).

## Goals

- The framework in full: every built-in from claim 1, story, networking, and the agent tools, published at Release 1.
- The demo game grows into the showcase as each piece lands, so every M2 plan ends with the demo using what it built.
- A first-time player learns what to do, how to do it, and that they did it, inside the game.
- A first-time developer or agent goes from the README to a new, running game that passes `automata check`.
- M2's plans are small and mostly independent, so several can run side by side.

## Non-goals

- Editors. They are M3; M2 writes the files they will change.
- Publishing: `automata ship`, itch.io, Wavedash and the desktop app are M4. M2's host adapters stop at `web` (and a
  test host).
- Deploying the room server, and online play in the demo. Online play is built and proven in CI; Fly.io hosts it
  once the 3D game uses it (the Owner, 2026-11-14).
- 3D, and anything that mixes it in.
- A light theme for the demo's screens.

## Anti-goals (failure even if it technically works)

- A built-in that works only in the demo game: each one is in the framework and used through the published package.
- A feature the demo game has that a new game from `automata create` does not get for free.
- A screen, sound or line of text that only a person can change: if an agent can't change it by editing a file, it is
  a defect.
- A golden that moves without the Owner seeing before and after.
- A plan that waits on another that has not merged. Plans that depend on each other say so and run in order.

## Decided with the Owner

| The showcase's shape | One short real game of three levels (about five minutes), where each feature turns up naturally, plus a "What's inside" page off the pause menu that lists every feature and where to see it (the Owner, 2026-11-14). |
| Editors | M3: World, Characters, Feel, Sound and Story. |
| Physics | Rapier's deterministic 2D build, as in M1. |
| Formats | Content JSON, everything else TOML. |
| Languages | Games ship English, Spanish, Korean, Japanese, Chinese and Portuguese. |
| Networking | Multiplayer-ready; the room server goes on Fly.io when it is deployed. |
| Built for agents | Small files, agent skills, an MCP server and a check command. |

## Approaches considered

1. **Small plans in tracks, the demo growing after each (chosen).** M2 is cut into about ten plans along the
   framework's feature layers. Plans with no dependency on each other run at the same time, each in its own thread
   and branch; each ends by moving the Examples pin and adding its feature to the demo. Chosen because it lets
   several threads work at once (the Owner, 2026-11-14: two working threads is not enough), keeps each pull request
   small, and makes the demo show progress all through M2.
2. **One M2 plan, executed in order.** Simpler to audit as a whole, but one thread for weeks, and the demo shows
   nothing until the end.
3. **Demo first, framework pulled out after.** Fastest to a playable showcase, but it builds features inside a game
   and lifts them later, which is what the anti-goals forbid.

## What M2 adds to the framework

Feature layers continue the M1 spec's order (sim, physics, commands, net, content, render, input, audio, saves,
locale, story, ui, screens, host, cli). Each item names its plan (see Plans).

### Content: the new files (plan C)

Each new file type has a Zod schema, a JSON Schema in `schemas/`, `file: path` diagnostics, and is written only by
`writeContent`. One thing per file, so two people (or a person and an agent) rarely touch the same one.

| Type | What it holds | Used by (M3 editor) |
|---|---|---|
| `tileset` | Tile images, their collision shapes, auto-tiling rules | World: Tiles |
| `backdrop` | Parallax layers and props, from a scene file | World: environment builder |
| `figure` | A character drawn from parts (the old figure file, 2D only) | Characters: figure builder |
| `character` (widened) | Clips (idle, run, jump, fall, land, push), the kind, its body | Characters: clips and kinds |
| `behaviour` | Rules for how a character decides | Characters: Schematic |
| `tuning` | Controls and movement numbers, each with a range | Feel: Tuner |
| `feel` | What happens when an event fires: dust, shake, freeze | Feel |
| `sound`, `music`, `cues` | Sounds made of tones and noise, music, what plays when | Sound |
| `conversation` | Branching lines and choices, with a message key per line | Story: Writer |
| `cutscene` | Camera and actor keys on a timeline | Story: Sequence |
| `messages` | One file per language: every word a player reads | (Story, later) |

The project file `automata.toml` lists every content file as today. My call: one `messages/<lang>.json` per language
is content (players read it, so the Story editor may change it later), not TOML.

### Art (plan A)

- The render feature plays sprite sheets and atlases, tilesets with auto-tiling, and parallax backdrops, with the
  camera following the players.
- `automata art` paints a figure or scene file into PNGs and an atlas beside it, deterministically (the same file
  makes the same bytes), with no paid service or model call. The M3 builders are screens over this. *My call: the
  painting moves here from M3 so the demo has real art in M2 and an agent can change art by editing a file.*
- The example games' art is in palette No. 276; the framework imposes no palette.

### Input (plan I)

Gamepad (the standard mapping), keyboard and touch, all mapped to the same actions; bindings players change on the
settings screen, saved with their settings. Up to four players, each with their own device (see Multiplayer).
Touch controls keep the M1 rule: the level is fitted above the buttons.

### Audio (plan S)

Sounds made of tones and noise and music, synthesised at run time from the `sound` and `music` files (no audio
files to ship, so an agent can change a sound by changing numbers); `cues` say what plays on which sim event.
Volume for music and for sound, saved with the settings. Audio observes the sim and never changes it, so sound never
moves a hash. Audio starts on the first tap or key, as browsers require, and says so ("Tap to start the sound")
rather than staying quietly silent.

### Saves (plan V)

Save slots for progress and one for settings, through the host port. The web host keeps them in the browser's
storage as its declared way of saving, and says so when the browser refuses; it never falls back quietly. A save
holds a version, and a game that loads an older one upgrades it or says it can't.

### Languages (plan L)

Paraglide messages from the `messages` files; the language is the player's saved choice, then the host's, then the
browser's, then English. The demo's fonts follow the Visual direction (Fredoka and its rounded Japanese, Korean and
Chinese partners). A check fails when a message is missing in any of the six languages. *My call: M2's translations
are written by an agent and marked for a native speaker's read before Release 1.*

### Story (plan T)

Conversations, behaviour rules and cutscenes run in the sim, so they are in the hash and in replays. A conversation's
choice is a player command. Cutscenes move the camera and actors on sim ticks; the player can skip one, and a skip is
a command too.

### UI, screens and layouts (plan U)

- A small Svelte 5 kit in the framework for a game's own screens: buttons, sliders, lists, a key-binding row; touch
  targets 44 px, primary actions 48 px; focus kept through rotation; works with keyboard, touch and gamepad alike.
- The screens every game gets: title, pause, settings (controls, sound, language), saves, and a "well done" screen.
  A game dresses them through CSS properties, as the touch buttons are today, and can replace any one.
- Layouts for phone, tablet and computer, upright and sideways, from the container's size.
- The framework's screens have plain words in all six languages and pass the drunk-grandma test.

### Host (plan V, with saves)

The host port grows from "is the game on screen" to saves, the language, links and quit. Adapters: `web` and a
`test` host for Node and journeys. itch.io, Wavedash and Tauri are M4.

### Networking (plan N)

The room server (`@automataframework/framework/server`, a Node entry on Colyseus, with Effect for its host process)
and the client, on the M1 spec's model: the server relays each tick's commands and runs the same sim; clients predict
their own commands, roll back and replay when the server's tick differs; periodic hashes catch a desync.

- Proven in CI: a room server and two headless players end on the same hash, with a lag and a late command forced so
  that rollback runs; and a journey with two real browsers against a server CI starts.
- The demo does not go online. Its co-op is same-screen (see Multiplayer in the demo), which runs every player
  through the same numbered commands the room server relays.

### The agent tools (plan K)

- `automata create <name>`: a new game from a template that already has every built-in, one level, a hero and the
  screens, and passes `automata check` with no change.
- `automata check`: lint, types, every content file against its schema, the replays, and the game's tests, with
  plain-words output that says which file and what to do.
- `automata play` and `automata replay`: run the game in a browser, and play a recorded replay to its hash.
- `automata art`: see Art.
- `automata mcp`: an MCP server over the same commands, plus reading the content schemas and a running game's state.
  *The tool list is the plan's.*
- Agent skills ship in the package: where things live, the rules a game keeps (the sim's laws, one file per thing),
  and how to add each kind of content.
- The README's first section takes a newcomer from nothing to a running game in a handful of commands, and a test
  follows those commands in a clean folder.

### Watch mode (plan U)

The game can play a recorded replay by itself, with a "Play" button over it that hands control to the player. The
site's redesign needs it for the game before Play.

### M1's deferred minors

The M1 implementation audit's nine minors (M1 to M9) are each fixed by the plan that touches that code: the first
frame (M1), replay after stop (M2) and broken-state (M3) by plan U; code-changed versus diverged (M4) and replay checks
(M5) by plan K; Zod's jitless in `/headless` (M6) by plan C; canvas density (M7) and tile seams (M8) by plan A; `.d.ts`
paths (M9) by plan K.

## The demo game as showcase

One short real game of three levels, about five minutes from the title screen to the last door (the Owner,
2026-11-14). It carries content for every editor (the M1 spec's table, widened to three levels) and shows each of
these where a player meets it:

| Feature | Where the player sees it |
|---|---|
| Physics | Crates, the seesaw, the swinging platform |
| Story | The keeper's conversation with a choice; a cutscene at a level's start and at the door |
| Behaviour rules | The critter that wanders and runs from the hero |
| Feel | Dust on landing, a shake when a crate drops, a freeze on a spark |
| Sound | Jump, land, spark, thud and door sounds; one music track; volume in settings |
| Menus | Title, pause, settings, saves, "well done" |
| Controls | Keyboard, touch and gamepad; changing a key in settings |
| Saves | Progress kept across a reload; a "Continue" on the title screen |
| Layouts | Phone, tablet and computer, upright and sideways |
| Languages | All six, picked in settings |
| Multiplayer | Same-screen co-op for 2 to 4 players; "Add a player" on the title and pause screens |
| Determinism | Watch mode plays the recorded run, which CI checks in four engines |

**Multiplayer in the demo.** Same-screen co-op (the Owner, 2026-11-14). A second, third or fourth player joins by
pressing a button on their own gamepad, or by taking the other half of the keyboard, and leaves from the pause screen.
*My calls:* touch is one player only (two people on one phone's buttons fails the drunk-grandma test); the camera
keeps every player on screen and zooms out as they spread, up to a limit, beyond which a player off screen is pulled
along; each player's hero is told apart by a colour from palette No. 276 and a number over its head; a level is done
when every player is through the door. The co-op replay is a golden of its own, beside the single-player one.

**What's inside.** A page off the pause menu lists every feature in the table above, in plain words, each with where
to see it ("Talk to the keeper at the start of level one"). It is built from a content file, so an agent adds a line
when it adds a feature. *My call: it is the demo's own screen, not a framework screen.*

**First-time player.** Level one teaches by doing: one action at a time (move, jump, push), each shown with the right
control for the device in use, and a clear sign when it is done. Nothing is explained that the player has not yet
needed.

**Goldens.** The demo's recorded play and the test game's play stay the goldens. A plan that changes the game's play
records a new one in CI and shows the Owner before and after.

## Plans

Each plan goes through the stages (plan, plan audit, execution, implementation audit, fixes, Owner review) on its own
branch. A plan in Examples that adds a feature to the demo starts only after the framework plan it uses has merged
and the pin has moved.

| Plan | Repo | Depends on |
|---|---|---|
| C. Content: the new file types and their schemas | Framework | — |
| A. Art: sprites, tilesets, backdrops, camera, `automata art` | Framework | C |
| I. Input: gamepad, remapping, up to four players | Framework | — |
| S. Audio | Framework | C |
| V. Saves and the host port | Framework | — |
| L. Languages | Framework | C, V |
| T. Story: conversations, behaviour, cutscenes | Framework | C |
| N. Networking | Framework | — |
| U. UI, screens, layouts, watch mode | Framework | I, S, V, L |
| K. The `automata` command, MCP, skills, README | Framework | C (and each other plan's content, as it lands) |
| D. The showcase demo | Examples | each framework plan, one step per plan |

Four can start at once (C, I, V, N); C's merge opens A, S, T and K; U waits on I, S, V and L. Plan D is a running
plan in Examples with one step per framework plan, each step its own pull request. The five-branch rule still holds,
so at most four plans are in CI at a time. The Site's redesign (watch mode) waits on U.

## Testing

- Every plan has unit tests, cross-engine parity for anything the sim touches (Node, Chromium, WebKit, Firefox), and
  end-to-end journeys in real browsers at phone, tablet and desktop sizes, upright and sideways.
- Journeys the demo must pass by the end of M2: a first-time player finishes level one on touch; a player changes a
  key and uses it; sound volume is kept across a reload; a save is continued; the language is changed and every
  screen shows it; a player meets the keeper, picks a choice and sees the cutscene; watch mode hands control to a
  player; a second player joins with a gamepad and both reach the door; and the two-browser journey against a room server CI
  starts.
- A test follows the README in a clean folder: `automata create`, `automata check`, a changed number, `automata check`
  again.
- Sound is tested by what plays when (the cue log), not by listening.

## Done means

On each repo's `main`, proven by CI:

- The demo game plays end to end with every built-in, shows every feature in the showcase table, and passes its
  journeys at phone, tablet and desktop sizes in Chromium, WebKit and Firefox; its recorded play hashes the same in
  all four engines.
- `automata create` makes a new game that passes `automata check`, and an agent through `automata mcp` can create,
  check, run and replay it.
- The room server and two players end on the same hash in CI, rollback included.
- The Owner has played the demo game and said it is fine.
