# A retro at the end of every slice

## Outcome

Every slice closes with a retro, after its design review loop and blind judge. A fresh session reads what the slice
produced (audits, open items, flaky tests, merged pull requests, failed CI runs), finds the problems that came back,
turns each one a program can catch into a test or check, and batches the rest into one rule-change pull request per
repo for the Owner to approve. This spec also carries the first retro's own output: one restored check and today's
rule edits.

## Owner approval

- 2026-11-16 19:17 UTC, project thread: "yes" to the coordinator's proposal of a retro that turns each lesson into a
  test where it can ("the footer check, for example") and proposes the rest as one rule-change pull request for the
  Owner to approve.
- 2026-11-16 19:18 UTC: "lets do self improving after every slice actually". So the retro runs when a slice closes, not
  on a daily schedule. No scheduled task is created.

Both cover this change only. The implementation pull requests are lane 3 and wait for the Owner's approval of the
finished result before they merge.

## Lane and path

Lane 3 (CLAUDE.md, `.claude/skills/` and a CI workflow file), staged path: this spec and its plan audit, then one
implementation pull request per repo with one implementation audit across them all, then the Owner's approval, then a
merge commit.

## Acceptance criteria

1. The five `review/SKILL.md` files are byte-identical after the change (one `md5sum`).
2. Each repo's `CLAUDE.md` diff against `main` holds only the three edits above (Slices, Settings, Limits), rewrapped to
   120 columns.
3. The "Slice retro" section says: when a slice closes, after the design review loop; a fresh session, Opus medium;
   who starts it; what it reads; repeat problems; checks first; lessons or rule edits otherwise, one pull request per
   repo, lane 3, Owner's approval; the retro record's path; the report to the coordinator; nothing to learn means no
   change.
4. A test fails on a description whose last line is the "Generated by Claude Code" footer, and on one with no
   "Requested by" line; it passes on one ending with `Requested by **McThayDT**` followed by blank lines.
5. The restored files match the repo's pre-removal copy except for the new rule and its tests (a `git diff` against
   the removal's parent shows only those).
6. `commit-authors` runs on each implementation pull request and passes once its body's footer is stripped.
7. Each `history.md` records the approval under "Rule changes"; Editors' and Site's carry the font lesson.
8. Every commit is authored and committed by McThayDT with no Claude credit; each body ends with
   `Requested by **McThayDT**`; each merges with a merge commit after the Owner approves.
9. CI is green on each pull request.
